## 先读懂：从一堆检测框到一条条轨迹

### 多目标跟踪要解决的三个问题

检测和跟踪的差距，可以用一句话说清：检测回答「这一帧画面里有什么」，跟踪回答「这一帧里的框是哪一帧那个目标的」。要回答第二个问题，必须同时处理三件事。

![检测与跟踪的区别](./images/fig-detection-vs-tracking.png)

目标在两帧之间会移动，运动模型要能预测它下一帧大致在哪，否则匹配无从谈起。新出现的目标要开一条新轨迹，离开画面的要关掉，中间反复开关就是 ID Switch（IDSW）。遮挡、运动模糊、目标交叉还会让检测框消失或跑到别人身上，关联层要做的是让这些错误止步在当帧，不传染到下一帧。

**一句话记忆：**检测给出「这一帧有什么」，跟踪给出「这是第几号目标」。

#### Tracking-by-Detection 与轨迹状态机

本章采用 **Tracking-by-Detection** 范式。

检测器负责逐帧找出目标，跟踪器则负责判断不同帧中的检测结果是否属于同一个目标，并持续维护对应的 Track ID。

> **检测器解决“这一帧里有什么”，跟踪器解决“它还是不是刚才那个目标”。**

例如，一个人从画面左侧走到右侧，检测器会在每一帧重新输出一个检测框。单独来看，这些框之间没有关系；跟踪器需要把它们关联起来，并让这个人在整个过程中保持同一个 ID。

## 每一帧发生了什么

一次完整的跟踪过程通常包含四个步骤：

![单帧跟踪流程示意](./images/fig-per-frame-pipeline.png)

1. **预测轨迹位置：** 根据目标此前的位置和运动趋势，预测它在当前帧可能出现的位置。

2. **匹配当前检测结果：**将当前帧的检测框与已有轨迹进行关联。匹配成功后，用新的检测结果更新轨迹的位置和运动状态。

3. **创建新轨迹：**如果某个检测框无法匹配任何已有轨迹，就为它创建一条新的候选轨迹。

4. **保留暂时失配的轨迹：**如果已有轨迹在当前帧没有找到对应检测框，不会立即删除，而是暂时保留，等待后续帧重新匹配。

这套机制能够处理检测器偶尔漏检、目标短暂遮挡等情况，也是后面轨迹状态机存在的原因。

## 轨迹状态机（原理示意）

下图的 Tentative / Confirmed / Lost / Deleted 是教学抽象；实机调用的是 `supervision.ByteTrack`，不要把这些英文标签当成项目自研消息字段或真实 ROS 接口。

![轨迹生命周期原理示意](./images/fig-track-state-machine.png)

一条轨迹并不是创建后就一直存在。

从目标第一次出现，到稳定跟踪，再到暂时消失或最终离开，轨迹会经历不同的生命周期状态：

```text
                    连续命中达到阈值
新检测 ──→ Tentative ─────────────→ Confirmed
              │                         │
              │ 确认前失配               │ 当前帧失配
              ↓                        ↓
           Deleted                   Lost
                                       │
                         ┌─────────────┴─────────────┐
                         │                           │
                     重新匹配                    超过保留窗口
                         │                           │
                         ↓                           ↓
                     Confirmed                    Deleted
```

四种状态可以概括为：

| 状态            | 含义              |
| ------------- | --------------- |
| **Tentative** | 刚发现目标，还需要继续观察   |
| **Confirmed** | 已确认目标，可以稳定输出    |
| **Lost**      | 暂时没有检测到，但轨迹仍然保留 |
| **Deleted**   | 轨迹生命周期结束，不再参与匹配 |

### Tentative：暂定轨迹

一个新目标第一次出现时，通常不会立刻被当成可靠轨迹，而是先进入 **Tentative** 状态。

原因很简单：单帧检测可能只是一次误检。只有连续命中达到 `minimum_consecutive_frames` 后，轨迹才会转为 Confirmed。若还没有达到确认条件就发生失配，则直接删除。

例如：

| `minimum_consecutive_frames` | 效果                 |
| ---------------------------- | ------------------ |
| `1`                          | 响应快，但误检更容易形成轨迹     |
| `3`                          | 更稳定，但新目标需要等待几帧才能确认 |

这个参数控制的，本质上是**轨迹确认速度与误检抑制之间的取舍**。

### Confirmed：已确认轨迹

当 Tentative 轨迹连续命中足够多帧后，就进入 **Confirmed** 状态。

此时跟踪器已经认为这个目标真实且稳定，可以正常输出 Track ID。

只要后续检测持续匹配成功，这个 ID 就会一直保留：

```text
Frame 120    ID = 7
Frame 121    ID = 7
Frame 122    ID = 7
```

如果某一帧没有找到对应检测框，轨迹不会立即消失，而是进入 Lost。

### Lost：暂时丢失

**Lost 并不意味着目标已经离开。**

它表示当前帧暂时没有检测到目标，但跟踪器仍然保留这条轨迹。

常见原因包括：

- 目标被其他物体短暂遮挡；

- 检测器偶尔漏检；

- 运动模糊；

- 光照变化；

- 目标短时间离开有效检测区域。

在 Lost 状态下，跟踪器仍可以根据历史运动状态继续预测目标的位置。

例如：

```text
Frame 100    ID = 5
Frame 101    未检测到
Frame 102    未检测到
Frame 103    重新检测到 → ID = 5
```

只要轨迹还没有被删除，第 103 帧重新出现的目标就有机会继续使用原来的 ID。因此，**Lost 状态决定了短暂遮挡之后能否继续接回原来的轨迹。**

### Deleted：轨迹结束

当一条轨迹进入 **Deleted**，它就不会再参与后续匹配。

通常有两种情况：

- Tentative 轨迹还没有确认，就已经发生失配；

- Lost 状态持续时间超过允许的保留窗口。

轨迹一旦删除，原来的 Track ID 也随之结束。即使同一个目标之后重新出现，也会被当作新的目标处理：

```text
原轨迹：ID = 5
        ↓
长时间丢失
        ↓
轨迹删除
        ↓
重新出现：ID = 12
```

从人的视角看，它可能还是同一个目标；但对跟踪器来说，原来的轨迹已经结束。

![短暂遮挡与轨迹删除后的 ID 变化](./images/fig-id-continuity.png)

### 轨迹还能保留多久

`lost_track_buffer` 控制一条 Lost 轨迹在没有检测结果的情况下，还能继续保留多少帧。

这个参数直接影响遮挡场景中的 ID 连续性。

| `lost_track_buffer` | 优势                           | 代价                               |
| ------------------- | ---------------------------- | -------------------------------- |
| **较大**              | 遮挡时间较长时，仍有机会接回原来的 ID；轨迹连续性更好 | 已离开画面的目标会被保留更久；可能出现短暂的“幽灵轨迹”     |
| **较小**              | 无效轨迹清理更快；画面中的轨迹更干净           | 短暂遮挡也可能导致轨迹被删除；目标重新出现时更容易获得新的 ID |

可以把它理解为一组直接的取舍：

> **更长的保留时间 → 更好的 ID 连续性**
> **更短的保留时间 → 更及时的轨迹清理**

### 不要只看帧数

`lost_track_buffer` 是按帧计的丢失缓冲；实际经过的秒数还取决于输入帧率。当前配置基数为 **90**，`frame_rate` 配为 **30**。下表仅展示「同样保留 90 个处理帧」在不同实际吞吐下的持续时间：

| 实际帧率   | 轨迹保留时间 |

## 卡尔曼预测与匈牙利匹配：各自解决什么

目标跟踪里，卡尔曼滤波和匈牙利算法经常一起出现，但两者解决的是完全不同的问题：

> **卡尔曼滤波负责预测“目标大概在哪里”，匈牙利算法负责判断“哪个检测框属于哪条轨迹”。**

### 卡尔曼滤波：预测目标在哪里

检测器给出的框会有抖动，也可能偶尔漏检，因此不能只依赖当前帧的位置。跟踪器通常会为每条轨迹维护一组状态，例如目标的**位置、尺寸和运动速度**。进入新的一帧后，卡尔曼滤波主要完成两个步骤：

1. **预测**：根据上一帧的运动状态，估计目标当前可能出现的位置；

2. **更新**：如果当前帧成功匹配到检测框，再利用新的观测修正预测结果。

可以理解成：

```text
上一帧状态
    ↓
运动模型预测
    ↓
预测位置
    ↓
匹配当前检测框
    ↓
用检测结果修正状态
```

卡尔曼滤波不仅维护“目标在哪”，还会维护这次估计的**不确定度**。连续几帧没有观测时，预测越来越不可靠，不确定度会逐渐增大；重新获得检测结果后，新的观测会帮助轨迹重新收敛。

所以它并不是简单地把“预测位置”和“检测位置”取平均，而是根据两边的不确定度决定应该相信谁更多。

### 匈牙利算法：决定检测框属于谁

完成预测以后，还有另一个问题：

假设当前已经有`N`条轨迹，同时检测到了`M`个目标，应该怎样把它们一一对应起来？

例如：

```text
已有轨迹                 当前检测

Track 1  ─────────────── Detection A
Track 2  ─────────────── Detection B
Track 3  ─────────────── Detection C
```

实际情况当然不会提前知道这些连线。跟踪器会先计算每一组“轨迹—检测框”的**匹配代价**，形成一张代价矩阵，再由匈牙利算法寻找整体代价较小的一组匹配关系。因此，匈牙利算法本身并不知道什么是目标，也不知道什么是 IoU。**它只负责根据已经计算好的代价完成分配。**真正决定跟踪效果的关键之一，是：

> **轨迹与检测框之间的代价到底怎么计算。**

### 常见的匹配依据

常见的匹配依据主要有三类：

| 匹配依据          | 判断什么               | 特点                   |
| ------------- | ------------------ | -------------------- |
| **IoU / 重叠度** | 预测框与检测框是否足够重合      | 计算简单、速度快             |
| **外观特征**      | 当前目标与历史目标在外观上是否相似  | 遮挡和交叉场景更有优势，但需要 ReID |
| **马氏距离**      | 检测位置是否落在预测轨迹的合理范围内 | 能结合卡尔曼滤波的不确定度        |

其中，**IoU 是最直接的做法**。预测框与检测框重叠越多，通常越可能属于同一个目标；如果匹配程度低于允许阈值，这组配对就会被排除。本章代码中的 `minimum_matching_threshold` 就参与了这类匹配结果的筛选。

但只看位置并不总是可靠。多人交叉、目标相互遮挡时，不同目标的框可能靠得很近，这也是 DeepSORT 引入 **ReID 外观特征**的原因。它会额外提取目标的视觉特征，用来判断当前检测到的人是否仍然是之前那个人。本章方案没有启用 ReID，因此不会利用这类外观信息。

**马氏距离**解决的是另一个问题：一个检测框虽然偏离预测位置，但这个偏差到底算不算异常？它不仅看距离本身，还会结合卡尔曼滤波维护的不确定度。轨迹预测越稳定，匹配范围可以越严格；连续丢失几帧后预测的不确定度增大，合理的搜索范围也会随之变化。

这些匹配依据并不是彼此独立的“算法流派”，实际跟踪器往往会根据自己的关联策略选择其中一种或组合使用。SORT、DeepSORT、ByteTrack 和 BoT-SORT 的区别也不只是换了一个距离函数，而是对**运动预测、匹配依据以及关联流程**做了不同设计。

| 算法            | 主要思路                                   |
| ------------- | -------------------------------------- |
| **SORT**      | 使用卡尔曼滤波预测运动，通过 IoU 完成轨迹与检测框的关联         |
| **DeepSORT**  | 在运动和位置匹配之外加入 ReID 外观特征，增强身份关联能力        |
| **ByteTrack** | 不依赖 ReID，充分利用低置信度检测框，减少因检测置信度下降造成的轨迹中断 |
| **BoT-SORT**  | 在关联策略上进一步加入相机运动补偿，并可结合 ReID 外观特征       |

其中，ByteTrack 值得特别注意。它的关键并不是发明了一种新的匹配距离，而是改变了**检测框参与关联的方式**：先使用高置信度检测框完成主要匹配，再让尚未匹配的轨迹与低置信度检测框进行第二次关联。

这样一来，目标即使因为遮挡、模糊等原因导致检测置信度暂时下降，只要检测框的位置仍然合理，就还有机会维持原来的轨迹，而不是立即因为“分数太低”被丢掉。下一节会继续展开这套两阶段关联机制。

> **参数名不能脱离具体实现来看。**
> 不同跟踪库即使使用相似的参数名，其含义、方向和取值范围也可能不同。例如同样写 `matching threshold = 0.8`，在不同实现中未必表示同一个条件。因此，本章涉及阈值时都会同时注明具体实现和实机参数名。

### ByteTrack 的两阶段匹配：低分框为什么还要用

前面说「预测框与检测框做匹配」，但没回答一个问题：**哪些框有资格进这张匹配表**。被遮挡的目标往往还能被检测到，只是**置信度掉到 0.1 到 0.3 之间**。常规做法在按分数过滤时就把它们扔了，于是轨迹断了。ByteTrack 的核心观察是：这些低分框里，有一部分恰恰是遮挡目标的位置。扔了它们，就等于放弃了最需要的那次观测。

所以它把匹配拆成两轮：

1. **第一轮**：高分框（分数 ≥ 激活门槛）对全部轨迹做匹配。

2. **第二轮**：剩下的低分框，只对第一轮**没匹配上的**轨迹再匹配一次。

两条约束是关键。低分框**只救已有轨迹，不起新轨迹**。否则画面里任何一片噪声都会变成一条新轨迹。而且第二轮的门槛通常比第一轮更严，因为低分框的位置本身就不太可信。

实机把这个机制收敛成一个参数：`track_activation_threshold`（0.25）决定「多高分才算数得上的检测」，低于它的框不能激活新轨迹，但仍有机会参与第二轮救援。

**一句话记忆：**高分框负责「发现新目标」，低分框负责「别把老目标弄丢」。

### 相机运动补偿：什么时候才需要

前面所有推理都默认相机不动。机器人在走、云台在转的时候，整幅画面会发生刚性位移，运动模型的「匀速」假设立刻失效：它外推的位置与实际检测位置可能差出上百像素，IoU 直接归零，轨迹断掉。相机运动补偿（Global Motion Compensation, GMC）要估计的就是这个刚性位移，做法是从相邻两帧估出一个全局变换，把预测位置一起搬过去。

如果机器人自带里程计或 IMU，还有一条更可靠的路：用外部运动信息把预测从相机坐标系转到世界坐标系，而不是从图像里反推。

> **本章实机未启用 GMC。** `supervision.ByteTrack` 不提供这个选项，`config/bytetrack.yaml` 里也没有对应参数。这一节保留下来是为了让你知道：将来换到移动相机场景时，这是首先要补的一块，而不是靠调 `lost_track_buffer` 能绕过去的。

### 从算法到实机参数：五个参数各自在改什么

`config/bytetrack.yaml` 里的五个参数直接对应 `supervision.ByteTrack` 的构造参数：

| 参数                           | 实机取值 | 它在改什么                     | 现象                                                                                  |
| ---------------------------- | ---- | ------------------------- | ----------------------------------------------------------------------------------- |
| `track_activation_threshold` | 0.25 | **高分检测**的门槛，也是新轨迹激活所依赖的分数 | 调高：轨迹更干净、更稳，但漏掉弱目标；调低：弱目标也能起轨迹，但噪声和不稳定随之进来。它**不是**「参与跟踪的检测的最低置信度」——低于它的框仍可能参与第二阶段关联 |
| `lost_track_buffer`          | 90   | 丢失轨迹的**缓冲基数**             | 调高：遮挡容忍变长，轨迹更不容易碎，代价是幽灵轨迹变久；调低：轨迹清得干净，但遮挡后容易换 ID。实际窗口还受 `frame_rate` 影响             |
| `minimum_matching_threshold` | 0.8  | 第一阶段关联允许的**最大匹配代价**       | 调大：匹配更宽松，能接受重叠更差的配对，轨迹更不容易断；调小：更严格，目标快速移动或框重叠差时容易断成新 ID。它只管第一阶段，不是所有阶段共用的阈值         |
| `frame_rate`                 | 30   | 与实际处理帧率对应的缩放因子            | 它参与丢失窗口的计算；输入吞吐变了而这里不改，运动预测与遮挡容忍窗口会偏离预期                                             |
| `minimum_consecutive_frames` | 1    | 轨迹连续匹配多少帧后才作为**稳定轨迹**对外使用 | 调大：抑制短暂误检产生的偶然轨迹，但新目标要等几帧才拿到稳定 ID                                                   |

还有两个并不影响跟踪行为、但看日志时会遇到的参数：`tracker_type`（固定为 `bytetrack`，这是实机唯一的跟踪器）与 `publish_log_throttle_ms`（日志节流，1000 ms）。

**`frame_rate` 与 `lost_track_buffer` 必须一起读。** 实际丢失窗口不是 `lost_track_buffer` 本身，而是：

```text
max_time_lost = int(frame_rate / 30 × lost_track_buffer)
```

按当前配置代入（`frame_rate = 30`、`lost_track_buffer = 90`），窗口是 90 个处理帧。约 30 FPS 时相当于 3 秒；若实际处理吞吐降至约 15 FPS 而配置未变，同样 90 帧约为 6 秒。

`config/bytetrack.yaml` 的注释写明 `frame_rate` 对应 `bev_detection` 在 Orin 上的观测吞吐。如果你把检测换成别的输入源、帧率变了，这个值也要跟着改，否则实际遮挡容忍窗口会偏离预期。

## 动手：把检测框接成一条轨迹话题

三步。所有命令在 J501 上执行，工作目录是 `$M4_CODE_ROOT`。前提是 4.1 的检测链路已经在跑，或者用仓库自带的 `mock_detection_publisher` 造检测流。

### 步骤 5：启动跟踪链路

把 4.1 的检测输出接成轨迹。最省事的方式是直接跑一键脚本：

```bash
cd "$M4_CODE_ROOT"
./scripts/m4/run_m4_2_demo.sh
```

脚本走课程硬件的 GMSL2 通路，自己拉起 `camera_adapter_node` 把上游图像转成跟踪节点期望的话题，再启动 `tracking_node` 与可视化节点。只想单跑跟踪节点的话，用 `tracking_demo.launch.py`，它的参数默认值已经把输入输出话题配好了。

### 步骤 6：验证 `/perception/tracks`

接下来不要只看话题是否存在，而要确认轨迹消息真的能消费。

```bash
ros2 topic info -v /perception/tracks
ros2 topic hz /perception/tracks
ros2 topic echo /perception/tracks --once
```

逐条核对：

- **消息类型**是 `vision_msgs/msg/Detection2DArray`，与 `/perception/detections` 相同。跟踪复用标准消息，没有自研的轨迹消息类型。

- **QoS** 与 4.1 一致（`BEST_EFFORT` / `KEEP_LAST` 深度 10 / `VOLATILE`）。两边都按传感器数据配置，订阅端也要用同样的 QoS。

- **每个检测框带了 `id`**。这个 `id` 就是轨迹编号，也是 4.1 刻意留空的字段：检测节点不填，跟踪节点才填。

`tracking_visualizer` 会额外发布 `/perception/tracking_debug_image`，画面上每个目标带着它的 ID。无头环境下可以用 `--no-gui` 跳过 `rqt_image_view`，但调试图仍然照发。

### 步骤 7：观察现象与调参

运行同一段场景，观察下面几种现象，再按对应参数定位问题：

```bash
# 改参数后重启节点，对比同一段场景
vim 4.2-multi-object-tracking/ros2/bev_tracking/config/bytetrack.yaml
```

| 现象             | 先看哪个参数                                                            |
| -------------- | ----------------------------------------------------------------- |
| 遮挡后 ID 立刻换掉    | `lost_track_buffer` 调大（同时确认 `frame_rate` 与实际帧率一致）                 |
| 目标已离开画面，框还在原地飘 | `lost_track_buffer` 调小                                            |
| 目标快速移动时轨迹频繁断   | 先查检测框是否稳定；确属第一阶段关联过严时，`minimum_matching_threshold` 调**大**         |
| 画面里噪声变成了轨迹     | `track_activation_threshold` 调高，或 `minimum_consecutive_frames` 调大 |
| 遮挡容忍的时长与预期差很多  | 检查 `frame_rate` 与实际输入帧率是否一致                                       |

改 `lost_track_buffer` 是最直观的一次实验：当前配置为 90，调大后同一段遮挡里 ID 更容易接回来，但目标真的走出画面后也会多留一会儿。把两次的现象记下来，比记住参数含义更有用。

## 常见问题与排障

### 同一目标的 ID 频繁跳变

- **现象**：目标在画面里连续可见，ID 却每隔几帧换一个。

- **原因**：按可能性排序。检测框位置本身抖动大（回到 4.1 查）、`minimum_matching_threshold` 过高导致稍微移动就配不上、或 `frame_rate` 与实际帧率不符让丢失窗口的时间长度被算错。

- **处理**：先把 `/perception/detections` 的调试图和 `/perception/tracks` 的调试图并排看，确认检测框本身是否稳定；检测没问题再调匹配门槛；最后核对 `frame_rate`。注意实机没有启用外观特征，所以**光靠调参无法解决「两个外观相似目标互相换 ID」**，那需要外观信息，是另一条路。

### 目标已离开画面但轨迹还在

- **现象**：目标走出画面后，原来的框还在边缘附近飘几帧。

- **原因**：这正是 `lost_track_buffer` 的设计行为：它保留 N 帧的丢失窗口，用来接回遮挡目标。目标是真离开还是被遮挡，跟踪器当帧分不出来。

- **处理**：确认这是遮挡需要还是幽灵轨迹的代价。调小 `lost_track_buffer` 能让轨迹清得更快，代价是遮挡后必然换 ID。这个取舍没有两全解，按场景选。

### 轨迹话题有数据，但下游收不到

- **现象**：`ros2 topic hz /perception/tracks` 正常，自己写的订阅端一条消息都收不到，也不报错。

- **原因**：QoS 不兼容。两个话题都用 `SensorDataQoS`（BEST_EFFORT），订阅端如果用默认的 RELIABLE，DDS 会判定无法对接，直接不建立连接，而且不报错。

- **处理**：`ros2 topic info -v` 确认发布端 QoS，订阅端改成 `rclcpp::SensorDataQoS()`（C++）或 `qos_profile_sensor_data`（Python）。

### 接上跟踪后，检测的空帧行为被改坏了

- **现象**：4.1 的检测链路本来每帧都发消息（含空帧），代码改了一版之后，遮挡场景下轨迹立刻断掉。

- **原因**：检测节点在 `detections` 为空时提前 return，不发消息。跟踪靠「这一帧没有观测到」来推进丢失计数，收不到消息就不算一次观测，趋近于「什么都没发生」。

- **处理**：回到 4.1 确认空帧契约仍然成立：每帧都发，空帧发空数组。改检测节点时不要顺手加「空框提前 return」。

> **下一步：**4.3 为像素赋予语义类别，再映射出地面候选掩膜；它不能证明无碰撞空间。当前跟踪 ID 与分割掩膜是独立输出，后续集成需要显式对齐时间戳，不能把规划中的集成写成已完成。
