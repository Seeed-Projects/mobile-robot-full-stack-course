## 课程概述

![课程概述](./images/XCQhblwpeo0Zu1x2vOecGZLcnyb.gif)

4.1 让模型在每一帧里画出了框，但框上没有名字：同一辆小车在第 10 帧和第 40 帧长得几乎一样，检测器不会告诉你它们是同一个目标。多目标跟踪（Multi-Object Tracking, MOT）补的就是这段身份连续性：它接收逐帧的检测框，输出带稳定 ID 的轨迹。

## 先读懂：从一堆检测框到一条条轨迹

### 多目标跟踪要解决的三个问题

检测和跟踪的差距，可以用一句话说清：检测回答「这一帧画面里有什么」，跟踪回答「这一帧里的框是哪一帧那个目标的」。要回答第二个问题，必须同时处理三件事。

目标在两帧之间会移动，运动模型要能预测它下一帧大致在哪，否则匹配无从谈起。新出现的目标要开一条新轨迹，离开画面的要关掉，中间反复开关就是 ID Switch（IDSW）。遮挡、运动模糊、目标交叉还会让检测框消失或跑到别人身上，关联层要做的是让这些错误止步在当帧，不传染到下一帧。

**一句话记忆：**检测给出「这一帧有什么」，跟踪给出「这是第几号目标」。

### Tracking-by-Detection 与轨迹状态机

本页用的是 Tracking-by-Detection 范式：检测器逐帧出框，跟踪器只负责把框串成轨迹。每一帧的流程固定为四步。

1. 预测：对每条已有轨迹，用运动模型外推它在当前帧的位置和不确定度。

2. 关联：把当前帧的检测框与预测位置做匹配，求总代价最小的配对。

3. 新建：没有匹配上任何轨迹的检测框，视为新目标，开一条暂定轨迹。

4. 删除：连续若干帧没有匹配上检测的轨迹，判定目标已离开，删除。

四步之间的差别在于「关联」用什么代价，以及「新建 / 删除」用多严的门槛。状态机里的每个状态都对应实机的一个参数：

| 状态 | 进入条件 | 离开条件与观测现象 |
| --- | --- | --- |
| 暂定（Tentative） | 新检测框未匹配上任何轨迹，新建轨迹 | 连续 `minimum_consecutive_frames` 帧都匹配上则转已确认；窗口内丢一次即删除。现象：误检不会立刻变成轨迹 |
| 已确认（Confirmed） | 暂定轨迹连续命中达到 `minimum_consecutive_frames` | 某帧未匹配则转丢失；现象：对外输出的稳定 ID 在这一状态产生 |
| 丢失（Lost） | 已确认轨迹某帧没匹配上检测，仍用预测值外推 | 丢失帧数超过实际丢失窗口则删除；期间又匹配上则恢复原 ID。现象：这是遮挡后能「接回原 ID」的唯一窗口 |
| 已删除（Deleted） | 丢失帧数超限，或该轨迹从未被确认 | 不可恢复。目标重新出现时只能拿到新 ID |

丢失窗口由 `lost_track_buffer` 与 `frame_rate` 共同决定，是遮挡场景里直接决定「能不能接回原 ID」的那一对参数：调大能把长时间遮挡的目标接回来，代价是目标真的离开画面后仍会有一段幽灵轨迹；调小则刚好相反。两者的换算关系见「从算法到实机参数」一节。

### 卡尔曼预测与匈牙利匹配：各自解决什么

这两件事经常被混在一起，其实分工很清楚。

**运动模型回答「它大概在哪」。** 只有带噪声的检测框时，目标「现在最可能在哪、有多不确定」需要两样东西：一个状态（位置、尺寸、速度）和一个不确定度。每帧先按运动模型把上一帧的状态外推到当前帧（不确定度随之变大，因为多了一帧的外推），再用匹配上的检测框把它拉回观测位置（不确定度随之变小）。「拉回多少」由两者各自的不确定度加权决定，而不是固定比例平均。

**匹配回答「哪个框属于哪条轨迹」。** 给定 N 条轨迹与 M 个检测框，怎样配对让总代价最小。SORT 家族四代算法的真正差异，全在代价怎么算：

- **重叠代价**：只问「预测框与检测框重叠多少」。代价超出阈值的配对直接判无效。实机的 `minimum_matching_threshold` 就是第一阶段这道代价阈值。

- **外观代价**：问「这个框看起来像不像我记住的那个目标」，需要额外交一个 ReID 网络。实机**未启用**。

- **马氏距离**：问「这个检测框离我预测的位置偏了几个标准差」，会随状态不确定度自动放松或收紧。实机未直接暴露。

四代算法在这里分岔：SORT 只用 IoU，遮挡超过一帧就换 ID；DeepSORT 加了外观特征，代价是每帧对每个框跑一次网络；ByteTrack 绕开了网络，改用低分框（下一节）；BoT-SORT 进一步加入相机运动补偿。

> 有一处读代码时最容易踩的坑：**同名参数在不同实现里语义不同**。写「阈值 0.8」而不写库名，等于没写。本章一律带库名与实机参数名。

### ByteTrack 的两阶段匹配：低分框为什么还要用

前面说「预测框与检测框做匹配」，但没回答一个问题：**哪些框有资格进这张匹配表**。

被遮挡的目标往往还能被检测到，只是置信度掉到 0.1 到 0.3 之间。常规做法在按分数过滤时就把它们扔了，于是轨迹断了。ByteTrack 的核心观察是：这些低分框里，有一部分恰恰是遮挡目标的位置。扔了它们，就等于放弃了最需要的那次观测。

所以它把匹配拆成两轮：

1. **第一轮**：高分框（分数 ≥ 激活门槛）对全部轨迹做匹配。

2. **第二轮**：剩下的低分框，只对第一轮**没匹配上的**轨迹再匹配一次。

两条约束是关键。低分框**只救已有轨迹，不起新轨迹**。否则画面里任何一片噪声都会变成一条新轨迹。而且第二轮的门槛通常比第一轮更严，因为低分框的位置本身就不太可信。

实机把这个机制收敛成一个参数：`track_activation_threshold`（0.25）决定「多高分才算数得上的检测」，低于它的框不能激活新轨迹，但仍有机会参与第二轮救援。

**一句话记忆：**高分框负责「发现新目标」，低分框负责「别把老目标弄丢」。

### 相机运动补偿：什么时候才需要

前面所有推理都默认相机不动。机器人在走、云台在转的时候，整幅画面会发生刚性位移，运动模型的「匀速」假设立刻失效：它外推的位置与实际检测位置可能差出上百像素，IoU 直接归零，轨迹断掉。相机运动补偿（Global Motion Compensation, GMC）要估计的就是这个刚性位移，做法是从相邻两帧估出一个全局变换，把预测位置一起搬过去。

如果机器人自带里程计或 IMU，还有一条更可靠的路：用外部运动信息把预测从相机坐标系转到世界坐标系，而不是从图像里反推。

> **本章实机未启用 GMC。** `supervision.ByteTrack` 不提供这个选项，`config/bytetrack.yaml` 里也没有对应参数。这一节保留下来是为了让你知道：将来换到移动相机场景时，这是首先要补的一块，而不是靠调 `lost_track_buffer` 能绕过去的。

### 从算法到实机参数：五个参数各自在改什么

`config/bytetrack.yaml` 里的五个参数直接对应 `supervision.ByteTrack` 的构造参数：

| 参数 | 实机取值 | 它在改什么 | 现象 |
| --- | --- | --- | --- |
| `track_activation_threshold` | 0.25 | **高分检测**的门槛，也是新轨迹激活所依赖的分数 | 调高：轨迹更干净、更稳，但漏掉弱目标；调低：弱目标也能起轨迹，但噪声和不稳定随之进来。它**不是**「参与跟踪的检测的最低置信度」——低于它的框仍可能参与第二阶段关联 |
| `lost_track_buffer` | 30 | 丢失轨迹的**缓冲基数** | 调高：遮挡容忍变长，轨迹更不容易碎，代价是幽灵轨迹变久；调低：轨迹清得干净，但遮挡后容易换 ID。**实际窗口不等于这个数**，它会被 `frame_rate` 缩放 |
| `minimum_matching_threshold` | 0.8 | 第一阶段关联允许的**最大匹配代价** | 调大：匹配更宽松，能接受重叠更差的配对，轨迹更不容易断；调小：更严格，目标快速移动或框重叠差时容易断成新 ID。它只管第一阶段，不是所有阶段共用的阈值 |
| `frame_rate` | 10 | 与实际处理帧率对应的缩放因子 | 它参与丢失窗口的计算，见下方公式；输入吞吐变了而这里不改，实际遮挡容忍窗口就会偏离预期 |
| `minimum_consecutive_frames` | 1 | 轨迹连续匹配多少帧后才作为**稳定轨迹**对外使用 | 调大：抑制短暂误检产生的偶然轨迹，但新目标要等几帧才拿到稳定 ID |

还有两个并不影响跟踪行为、但看日志时会遇到的参数：`tracker_type`（固定为 `bytetrack`，这是实机唯一的跟踪器）与 `publish_log_throttle_ms`（日志节流，1000 ms）。

**`frame_rate` 与 `lost_track_buffer` 必须一起读。** 实际丢失窗口不是 `lost_track_buffer` 本身，而是：

```text
max_time_lost = int(frame_rate / 30 × lost_track_buffer)
```

按实机配置代入（`frame_rate = 10`、`lost_track_buffer = 30`），实际窗口是 10 帧。把 `lost_track_buffer` 直接读成「保留 30 帧」会高估三倍。

`config/bytetrack.yaml` 的注释写明 `frame_rate` 对应 `bev_detection` 在 Orin 上的观测吞吐。如果你把检测换成别的输入源、帧率变了，这个值也要跟着改，否则实际遮挡容忍窗口会偏离预期。

### 指标口径：这些数字本章为什么不产出

跟踪质量的标准指标是 MOTA 与 IDF1：

- **MOTA** 偏向检测与建档的误差，把漏检、误检、ID 切换合在一起罚。它更容易受检测质量影响，结果甚至可能为负。

- **IDF1** 只关心身份是否被认对，在遮挡与交叉多、ID 反复跳变时更有参考价值。

两个指标要一起看：MOTA 高而 IDF1 低，说明位置跟住了但认错了人。

**但本章不产出这两个数字**，原因是它们都需要逐帧的人工标注真值，而实机没有这份标注，也没有评估脚本。可用的替代观测是「同一目标的 ID 在连续帧里是否保持」，这也正是步骤 7 要你观察的东西。真要量化，得先补一份带标注的测试序列，那是另一件事。

## 动手：把检测框接成一条轨迹话题

三步。所有命令在 J501 上执行，工作目录是 `/home/seeed/workspace/ros2_bev`。前提是 4.1 的检测链路已经在跑，或者用仓库自带的 `mock_detection_publisher` 造检测流。

### 步骤 5：启动跟踪链路

把 4.1 的检测输出接成轨迹。最省事的方式是直接跑一键脚本：

```bash
cd /home/seeed/workspace/ros2_bev
scripts/m4/run_m4_2_demo.sh
```

脚本走课程硬件的 GMSL2 通路，自己拉起 `camera_adapter_node` 把上游图像转成跟踪节点期望的话题，再启动 `tracking_node` 与可视化节点。只想单跑跟踪节点的话，用 `tracking_demo.launch.py`，它的参数默认值已经把输入输出话题配好了。

### 步骤 6：验证 `/perception/tracks`

接下来不要只看话题是否存在，而要确认轨迹消息真的能消费。

```bash
ros2 topic info -v /perception/tracks
ros2 topic hz /perception/tracks
ros2 topic echo /perception/tracks --once
```

逐条核对：

- **消息类型**是 `vision_msgs/msg/Detection2DArray`，与 `/perception/detections` 相同。跟踪复用标准消息，没有自研的轨迹消息类型。

- **QoS** 与 4.1 一致（`BEST_EFFORT` / `KEEP_LAST` 深度 10 / `VOLATILE`）。两边都按传感器数据配置，订阅端也要用同样的 QoS。

- **每个检测框带了 `id`**。这个 `id` 就是轨迹编号，也是 4.1 刻意留空的字段：检测节点不填，跟踪节点才填。

`tracking_visualizer` 会额外发布 `/perception/tracking_debug_image`，画面上每个目标带着它的 ID。无头环境下可以用 `--no-gui` 跳过 `rqt_image_view`，但调试图仍然照发。

### 步骤 7：观察现象与调参

运行同一段场景，观察下面几种现象，再按对应参数定位问题：

```bash
# 改参数后重启节点，对比同一段场景
vim ros2_ws/src/bev_tracking/config/bytetrack.yaml
```

| 现象 | 先看哪个参数 |
| --- | --- |
| 遮挡后 ID 立刻换掉 | `lost_track_buffer` 调大（同时确认 `frame_rate` 与实际帧率一致） |
| 目标已离开画面，框还在原地飘 | `lost_track_buffer` 调小 |
| 目标快速移动时轨迹频繁断 | 先查检测框是否稳定；确属第一阶段关联过严时，`minimum_matching_threshold` 调**大** |
| 画面里噪声变成了轨迹 | `track_activation_threshold` 调高，或 `minimum_consecutive_frames` 调大 |
| 遮挡容忍的时长与预期差很多 | 检查 `frame_rate` 与实际输入帧率是否一致 |

改 `lost_track_buffer` 是最直观的一次实验：它原本是 30 帧，调大后同一段遮挡里 ID 更容易接回来，但目标真的走出画面后也会多留一会儿。把两次的现象记下来，比记住参数含义更有用。

## 产出物与验收标准

### 交付清单

1. 一条跑起来的跟踪链路：`scripts/m4/run_m4_2_demo.sh` 正常启动，`/perception/tracks` 持续发布。

2. 轨迹契约的验证记录：`ros2 topic info -v` 的类型与 QoS、`ros2 topic echo` 里带上 `id` 的检测框摘录。

3. 一次调参对比：至少改一个参数（建议 `lost_track_buffer`），记录改动前后的现象差异。

4. 一段可视化证据：`/perception/tracking_debug_image` 的截图，画面上带 ID。

### 验收标准

| 检查项 | 通过标准 | 不通过时优先检查 |
| --- | --- | --- |
| 链路连通 | `tracking_node` 正常启动，`/perception/tracks` 有数据且频率与检测输入相符 | 上游 `/perception/detections` 是否在发；`camera_adapter_node` 是否漏起 |
| 消息契约 | 类型为 `vision_msgs/msg/Detection2DArray`；QoS 与 4.1 一致 | 订阅端是否用了默认 RELIABLE QoS |

| 连续性 | 同一条连续轨迹在遮挡前后保持同一个 `id`（在 `lost_track_buffer` 覆盖的时长内） | `lost_track_buffer` 是否过小；`frame_rate` 是否与实际帧率不符 |
| 参数生效 | 改 `config/bytetrack.yaml` 后重启，行为随之变化 | 改的是不是 `bev_tracking` 的那份配置；包是否重新安装（Python 包改配置后需重装或直接改 install 下的副本） |

## 常见问题与排障

### 同一目标的 ID 频繁跳变

- **现象**：目标在画面里连续可见，ID 却每隔几帧换一个。

- **原因**：按可能性排序。检测框位置本身抖动大（回到 4.1 查）、`minimum_matching_threshold` 过高导致稍微移动就配不上、或 `frame_rate` 与实际帧率不符让丢失窗口的时间长度被算错。

- **处理**：先把 `/perception/detections` 的调试图和 `/perception/tracks` 的调试图并排看，确认检测框本身是否稳定；检测没问题再调匹配门槛；最后核对 `frame_rate`。注意实机没有启用外观特征，所以**光靠调参无法解决「两个外观相似目标互相换 ID」**，那需要外观信息，是另一条路。

### 目标已离开画面但轨迹还在

- **现象**：目标走出画面后，原来的框还在边缘附近飘几帧。

- **原因**：这正是 `lost_track_buffer` 的设计行为：它保留 N 帧的丢失窗口，用来接回遮挡目标。目标是真离开还是被遮挡，跟踪器当帧分不出来。

- **处理**：确认这是遮挡需要还是幽灵轨迹的代价。调小 `lost_track_buffer` 能让轨迹清得更快，代价是遮挡后必然换 ID。这个取舍没有两全解，按场景选。

### 轨迹话题有数据，但下游收不到

- **现象**：`ros2 topic hz /perception/tracks` 正常，自己写的订阅端一条消息都收不到，也不报错。

- **原因**：QoS 不兼容。两个话题都用 `SensorDataQoS`（BEST_EFFORT），订阅端如果用默认的 RELIABLE，DDS 会判定无法对接，直接不建立连接，而且不报错。

- **处理**：`ros2 topic info -v` 确认发布端 QoS，订阅端改成 `rclcpp::SensorDataQoS()`（C++）或 `qos_profile_sensor_data`（Python）。

### 接上跟踪后，检测的空帧行为被改坏了

- **现象**：4.1 的检测链路本来每帧都发消息（含空帧），代码改了一版之后，遮挡场景下轨迹立刻断掉。

- **原因**：检测节点在 `detections` 为空时提前 return，不发消息。跟踪靠「这一帧没有观测到」来推进丢失计数，收不到消息就不算一次观测，趋近于「什么都没发生」。

- **处理**：回到 4.1 确认空帧契约仍然成立：每帧都发，空帧发空数组。改检测节点时不要顺手加「空框提前 return」。

> **下一步：**4.3 语义分割接管「每个像素能不能走」的问题。跟踪给出的 ID 和分割给出的可行驶区域在 4.5 会被放在同一条链路上，那时你会看到两者对时间戳的要求是一致的：都依赖检测与相机图像共享同一个 `header.stamp`。如果这一章里你把 ID 观察清楚了，4.5 的集成会顺很多。
